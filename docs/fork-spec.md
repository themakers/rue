# Техническое задание: кроссплатформенный форк veact (Web + React Native)

**Статус:** черновик для исполнения агентом
**Роль исполнителя:** аудит, адаптация и валидация форка библиотеки `veact`
**Исходный репозиторий:** https://github.com/veactjs/veact (MIT, ~200 строк glue-кода поверх `@vue/reactivity`)

---

## 1. Идея и мотивация

Мне нужна ментальная модель Vue (мутабельная реактивность: `ref`, `reactive`, `computed`, `watch`, `watchEffect`, `effectScope`) внутри React-компонентов, при этом рендер-слой остаётся чистым React/JSX. Библиотека `veact` реализует ровно это: она реэкспортирует `@vue/reactivity` и добавляет тонкий слой React-хуков (`useRef`, `useReactive`, `useComputed`, `useWatch`, `onMounted` и т.д.), которые привязывают реактивные данные к жизненному циклу React-компонента и триггерят ререндер при мутациях.

API veact меня полностью устраивает. Проблема — veact писался и используется автором только для web (react-dom). Мне нужен **один state-слой для всех моих целевых платформ** («golden hammer»):

1. **Web** — React + react-dom (Vite; SSR на данном этапе не обязателен, но не должен быть архитектурно заблокирован).
2. **Mobile** — React Native + Expo (движок Hermes).
3. **Mobile/универсальный UI** — React Native + React Strict DOM (RSD).

Я готов взять форк на долгосрочную поддержку, поэтому приоритет — минимальная площадь собственного кода: вся реактивная механика должна оставаться в peer-зависимости `@vue/reactivity`, форк поддерживает только клей.

## 2. Ключевые архитектурные тезисы (проверить, а не принимать на веру)

Эти тезисы сформированы по предварительному анализу; фаза 0 обязана их подтвердить или опровергнуть.

- `@vue/reactivity` — чистый JS (Proxy / Reflect / WeakMap / Symbol), без зависимостей от DOM. Hermes всё это поддерживает (MobX 6 и Valtio работают в RN на тех же примитивах). Значит, слой 1 кроссплатформенен «из коробки».
- Единственный платформенно-опасный слой — glue-код veact. Исторически опубликованная npm-версия экспортировала `batchedUpdates === ReactDOM.unstable_batchedUpdates`, то есть имела жёсткий импорт `react-dom` — это фатально для RN. В текущем `main` этого экспорта в `src/index.ts` уже нет, но нужно проверить весь `src/` и опубликованную сборку.
- React Strict DOM ортогонален state-слою: RSD — это компоненты и стили (`html.*`), он не накладывает требований на управление состоянием. Если форк работает с голым React на обоих рендерерах — он работает и под RSD. Отдельной интеграции не требуется, требуется только smoke-проверка в примере.
- Механизм триггера ререндера — главная точка риска для React 18/19 concurrent rendering (tearing). Целевой механизм — `useSyncExternalStore` (API из пакета `react`, одинаково работает на web и в RN).

## 3. Требования к результату

### 3.1 Функциональные

- **F1.** Публичный API форка идентичен API veact `main` (список: `onMounted`, `onUpdated`, `onBeforeUnmount`, `useRef`, `useShallowRef`, `useCustomRef`, `useReactive`, `useShallowReactive`, `useReadonly`, `useShallowReadonly`, `useComputed`, `watch`, `useWatch`, `watchEffect`, `useWatchEffect`, `useEffectScope`, `useReactivity`, плюс полный реэкспорт `@vue/reactivity`). Breaking changes допустимы только если фаза 0 покажет, что текущее поведение несовместимо с concurrent rendering или RN, — каждый такой случай фиксировать в `MIGRATION.md` с обоснованием.
- **F2.** Мутация реактивных данных (в обработчиках, в `watch`-колбэках, в async-коде, в таймерах) приводит к корректному ререндеру подписанных компонентов на всех трёх целевых платформах.
- **F3.** `watch`/`watchEffect`, созданные через `use*`-хуки, автоматически отписываются при размонтировании компонента; scope-варианты уважают `effectScope` (`pause`/`resume`/`stop`, `onScopeDispose`).
- **F4.** Корректная работа в `<React.StrictMode>` (double-invoke рендеров и эффектов в dev): не должно оставаться утёкших effect'ов, задвоенных watcher'ов, ложных срабатываний `onMounted`.
- **F5.** Модульно-уровневые (вне компонентов) `ref`/`reactive` + `useReactivity` работают как глобальный стор, разделяемый между компонентами.

### 3.2 Платформенные

- **P1.** Ноль импортов из `react-dom`, `react-native` и любых platform-specific пакетов в runtime-коде библиотеки. Разрешён только пакет `react`. Проверяется автоматически (lint-правило или скрипт в CI, greр по исходникам и по собранному бандлу).
- **P2.** Не использовать `unstable_batchedUpdates` вовсе — в React 18+ батчинг автоматический. Если фаза 0 обнаружит места, где отсутствие ручного батчинга меняет наблюдаемое поведение, — задокументировать и решить через дизайн подписки, а не через платформенные entry points.
- **P3.** Один бандл для всех платформ: ESM + CJS, `exports` map без platform-условий, `sideEffects: false`, таргет синтаксиса, совместимый с Hermes (без down-level костылей под старые браузеры, но и без фич, которых нет в Hermes; ES2017-таргет — безопасная база, проверить актуальную поддержку Hermes на момент выполнения).
- **P4.** `react` и `@vue/reactivity` — peer dependencies. В `README` — предупреждение о недопустимости двух экземпляров `@vue/reactivity` в дереве (у standalone-сборки и пре-бандленной разные внутренние хранилища реактивных связей; ситуация актуальна, если в проекте одновременно живёт Vue).

### 3.3 Concurrent rendering

- **C1.** Подписка компонента на реактивные данные реализуется через `useSyncExternalStore` (напрямую из `react`; shim `use-sync-external-store` — только если решим поддерживать React < 18, по умолчанию — нет, минимальная поддерживаемая версия React 18).
- **C2.** `getSnapshot` обязан быть чистым, дешёвым и возвращать стабильное значение между мутациями (паттерн «version counter»: каждый триггер реактивного эффекта инкрементирует счётчик; снапшот — число). Это устраняет tearing: при мутации стора во время transition React сам перезапустит обновление как блокирующее.
- **C3.** `getServerSnapshot` предоставить (возврат текущей версии) — чтобы не блокировать будущий SSR, даже если сейчас он не используется.
- **C4.** Написать регрессионный тест на tearing: два компонента читают один `reactive`, мутация происходит внутри `startTransition`, ассерт — оба компонента после коммита показывают одну версию данных.

### 3.4 Нефункциональные

- **N1.** TypeScript strict, типы публичного API не деградируют относительно veact.
- **N2.** Покрытие glue-кода тестами ≥ 90% строк (кода мало, это достижимо).
- **N3.** Размер: не более ~3 КБ min+gzip собственного кода (без `@vue/reactivity`).
- **N4.** Совместимость с Fast Refresh (web/Vite) и Expo Fast Refresh: hot-reload компонента не должен плодить подписки/watcher'ы.

### Фаза 2 — Рефакторинг glue-слоя

1. Реализовать единый внутренний примитив подписки: `ReactiveEffect`/`watch` из `@vue/reactivity` + version counter + `useSyncExternalStore` (C1–C3). Все `use*`-хуки переводятся на него.
2. Убедиться, что установка watcher'ов идемпотентна при StrictMode double-invoke: создание эффектов — в `useState(() => ...)`-инициализаторе или в subscribe-фазе uSES, очистка — в unsubscribe; никаких эффектов, создаваемых в теле рендера без защиты.
3. `useEffectScope`: увязать жизненный цикл scope с mount/unmount так, чтобы при StrictMode повторный mount создавал свежий scope, а stop() старого гарантированно вызывался.
4. Lifecycle-хуки: `onMounted` → `useEffect` (не layout), `onUpdated` — пропуск первого рендера, `onBeforeUnmount` → cleanup. Поведение зафиксировать тестами.
5. Удалить/не восстанавливать `batchedUpdates` из публичного API (P2). В `MIGRATION.md` — заметка для переезжающих с оригинального veact.

## 6. Известные риски и тонкости (держать в голове при реализации)

- **Двойной экземпляр `@vue/reactivity`.** Если приложение одновременно использует Vue и форк, реактивные связи не будут разделяться между экземплярами пакета. Решение — peer dependency + предупреждение в README; дедупликацию не изобретать.
- **`flush`-семантика.** veact заявляет, что его `watch`/`watchEffect` не поддерживают `option.flush` (в Vue она завязана на планировщик рендера Vue, которого здесь нет). Не пытаться эмулировать `flush: 'post'` через рендерер — это затащит платформенную зависимость. Зафиксировать «flush всегда sync» в доках.
- **Чтение `.value` в JSX vs подписка.** Подписка должна происходить на данные, созданные/зарегистрированные хуками, а не на «что угодно, прочитанное в рендере». Если аудит покажет, что оригинал трекает чтения в рендер-фазе через глобальный activeEffect — это опасно в concurrent-режиме (рендер может быть отброшен). Предпочтительная модель: подписка на уровне хука (каждый `useRef`/`useReactive`/`useComputed`/`useReactivity` подписывает компонент на свой объект целиком). Это чуть менее гранулярно, но детерминированно и concurrent-safe. Решение зафиксировать в `architecture.md`.
- **`onUpdated` в concurrent-режиме** может вызываться чаще/реже наивных ожиданий; определить семантику как «после каждого коммита, кроме первого» и покрыть тестом.
- **Expo Go vs dev build:** примеры не должны требовать нативных модулей — библиотека чисто JS, следить, чтобы это оставалось так.
- **Fast Refresh** пересоздаёт state хуков частично; убедиться, что unsubscribe в uSES корректно гасит старые эффекты (иначе — накопление watcher'ов при каждом сохранении файла в dev).

## 7. Вне скоупа (non-goals)

- Options API / `defineComponent`-обёртка — возможное будущее расширение, не в этом ТЗ.
- Поддержка React < 18, классовых компонентов, Preact.
- SSR/RSC как полноценный сценарий (только «не блокировать архитектурно», C3).
- DevTools-интеграция, time-travel, персистенция.
- Изменение или векторизация самого `@vue/reactivity` — ядро используется как чёрный ящик.
